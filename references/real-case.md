# 真实案例：从微信公众号文章制作团队 Skill

## 背景

任务是读取一篇微信公众号文章，将其中的方法整理为可供团队安装和调用的 Codex Skill。验收标准包括：读到正文、形成有效的 `SKILL.md`、补齐使用说明并通过结构校验。

## 可复核事实

执行记录中出现了以下事件：

1. 默认 `python` 命令不存在。
2. 本地内容提取服务先被沙箱阻止，放开后仍连接失败。
3. 网页直接读取失败。
4. 一条浏览器代理路径因缺少依赖而不可用。
5. 浏览器打开文章时多次超时，留下 4 个相同 URL 的标签页。
6. 最终复用已经加载成功的标签页，只提取页面正文，完成文章阅读和 Skill 编写。

本次任务没有保存逐调用 Token、缓存命中或供应商费用。因此，案例只做方向性判断，不声称具体节省比例。

## 审计结论

最大浪费不是最终正文或 Skill 文件本身，而是成功路径确定前的失败空转：不可用的运行时、不可达的本地服务、缺失依赖，以及超时后重复创建页面。

| 发现 | 证据 | 成本机制 | 优先改进 |
|---|---|---|---|
| 工具路径缺少就绪检查 | 命令不存在、服务连接失败、依赖缺失 | 每次失败都增加调用、等待和上下文记录 | 调用前检查命令、服务和依赖是否可用 |
| 超时后重复创建资源 | 同一 URL 留下 4 个标签页 | 重复页面加载、重复等待、状态分叉 | 超时后先枚举并复用已有页面，不立即新建 |
| 工具返回范围过大 | 任务只需要正文 | 无关页面结构进入上下文 | 默认只提取标题、作者、正文和必要元数据 |
| 缺少统一成本埋点 | 无法精确核算 Token 与金额 | 只能判断方向，不能验证收益 | 记录路径、耗时、成功状态、Token、缓存命中和重试原因 |

## 推荐改造

### 1. 路由前置检查

在进入内容提取路径前，检查运行时、依赖和服务健康状态；不可用时立即切到下一条已知可用路径，不让模型反复尝试同类失败命令。

### 2. 资源复用与熔断

给“打开页面”设置幂等键，例如标准化 URL。发生超时时，先查询是否已有相同页面已经加载；同一路径连续失败达到阈值后熔断，避免继续堆叠标签页和重试记录。

### 3. 最小化工具载荷

成功加载页面后，只返回任务需要的正文与少量元数据。截图、完整 DOM 和无关导航元素仅在正文提取失败时按需获取。

### 4. 建立可量化基线

每次尝试至少记录：

- 工具路径与调用次数
- 成功、失败、超时及失败原因
- 输入、缓存输入和输出 Token
- 墙钟耗时
- 是否产出最终验收结果

随后以“每个验收通过任务的总成本”为主指标，对比改造前后相同任务集。

## 验证方式

用一组需要读取网页并生成结构化成果的任务做前后对照。质量守门指标保持不变，同时比较：

- 单任务失败调用数
- 重复资源数
- 成功任务总 Token 与总费用
- P50/P95 完成时延
- 首次可用路径命中率

如果正文完整度或成果校验通过率下降，则回滚载荷裁剪或路由规则；不能用降质换取表面成本下降。

# LLM 与 Agent 成本审计手册

在以下任务中读取本手册：完整系统审计、埋点设计、成本方案比较、缓存或模型路由设计、Agent 循环与多 Agent 评估。只回答一个概念性问题时不必加载。

## 1. 建立统一成本口径

优先使用“每个验收通过任务的总成本”，而不是孤立的 Token 总数：

```text
任务总成本
= 所有模型调用费用
+ 工具、检索、沙箱与相关基础设施费用
+ 为该任务发生的复核、重试和子任务费用

单位验收通过任务成本
= 观察窗口内的任务总成本 / 验收通过任务数
```

模型调用费用需按供应商实际账单项拆分，例如非缓存输入、缓存输入、输出、推理或其他计费项。不要在未核实价格和 usage 字段语义时套用固定公式。验收通过数为零时，单位成本为不可计算。

同时保留：

- 任务成功率与关键场景通过率。
- P50/P95 端到端时延。
- 每任务调用数、重试数、子 Agent 数与工具调用数的分布。
- 冷缓存、热缓存和缓存过期重建的分组结果。
- 质量、安全和权限边界的守门指标。

## 2. 最小证据集

能取得多少就使用多少，并清楚标注缺口：

- 任务类别、验收标准、请求量和观察窗口。
- 模型、供应商、区域、服务等级、价格日期与币种。
- 每次调用的输入、缓存输入、输出和其他计费字段。
- 调用链、失败类型、重试原因、超时、停止原因和最终结果。
- 系统提示、工具 schema、RAG 片段、会话历史和工具返回的大小分布。
- 缓存键、命中、写入、读取、过期和失效策略。
- 子 Agent 的输入、输出、结果复用和汇总方式。
- 质量评测、安全检查和用户可感知时延。

缺少日志时，先设计可观测性，不给出虚假的精确节省比例。

## 3. 按价值顺序检查



### 3.1 重复与失败工作

先找最直接的浪费：同一材料重复读取、相同条件下反复失败、超时后整段重跑、验收已经通过仍继续调用、子 Agent 重做主 Agent 已完成的工作。

检查四类程序化停止条件：

1. 验收通过即结束。
2. 达到费用、轮次或时间预算时保存状态并交付未完成项。
3. 相同条件重复失败且没有新证据时中断。
4. 缺权限或需要高风险审批时交给人决策。

重试应分类：网络故障有限退避；参数错误先修参数；权限错误停止；超时后先确认远端状态。写操作使用幂等键或业务去重，并从检查点恢复。

### 3.2 上下文、RAG 与长期状态

- 网页提取正文；日志折叠重复项；表格先筛选聚合；代码先搜索符号和调用点。
- RAG 按“权限与版本过滤 → 检索 → 去重/排序 → 按证据预算组装”执行，不固定塞满若干段。
- 证据保留来源、位置、数值和单位；不足时扩大检索或声明不足，不强行补全。
- 原始材料单独保存。工作状态只保留目标、约束、已确认事实、产物位置、未决问题和下一步。
- 摘要不是唯一记忆；关键权限、约束和原始证据要独立保留。
- 会话续接、服务端状态与 Compaction 的计费和语义因供应商而异，不能把“无需手工传历史”当成“历史免费”。



### 3.3 缓存

- 稳定规则、工具定义和输出约定靠前；本轮输入、时间戳和随机 ID 靠后。
- 保持工具顺序和 schema 确定，检查中间件是否重复注入。
- 分别计算冷启动、写入、读取、命中和过期重建；Prompt Cache 通常复用前缀计算而不是答案，具体计费以官方文档为准。
- 工具结果缓存与最终答案缓存分开设计。缓存键至少考虑租户、权限、数据版本和查询条件，并明确失效规则。
- 比较摘要生成与缓存重建的总费用；更短的前缀不一定比已命中的长前缀更便宜。



### 3.4 工具、Skill 与 MCP

- 常用小工具集可常驻；大型或低频目录按需发现。延迟加载会增加发现步骤，供应商或客户端开关不可假定通用。
- 在工具端裁剪：搜索返回片段，查询只返必要字段，测试返回状态与失败摘要；完整数据按需分页读取。
- 由程序强制字段、数量、字节数和执行时间上限；截断时返回标记或游标。
- 过滤、排序、聚合、连接和格式转换留在程序侧。模型只接收结果、异常和解释所需证据。
- 检查工具 schema 本身的 Token、重复描述、不可用工具、无效探测调用和过大的错误堆栈。



### 3.5 模型、推理与输出

- 用任务评测选达到门槛的最低成本模型，不默认最大模型。
- “低成本模型尝试 → 校验 → 升级”必须核算完整链路；若经常升级，级联可能更贵、更慢。
- 推理力度与可见输出分别控制。简单任务可评估较低推理；高风险或复杂任务按需升级。
- 用明确交付物代替“简洁一点”：规定结论、依据、待确认问题、文件或 diff、来源 ID 等。
- 机器消费输出可结构化，但仍要校验业务语义并允许缺失值和不确定性。
- 过低硬上限可能造成不完整答案和返工；“只给结论”也不等于没有隐藏推理成本。



### 3.6 多 Agent 与 AI 编程

- 多 Agent 是能力和并行策略，不是降本开关。只拆分独立、可验证且协调成本可控的任务。
- 子 Agent 只接收必要目标、证据和预算，返回结论与来源，不复制完整主会话。
- 代码任务先定位、再局部读取、再提交补丁；依赖目录和生成物不默认读取，不重印未修改文件。
- 测试范围与风险匹配。检查通过且无新修改、失败或疑点时停止；代码或环境变化后只重跑相关检查。



### 3.7 其他计费与架构选项

- 非实时任务可评估 Batch 或低优先级服务。这类方案通常改变单价和时延，不减少任务本身 Token。
- 高频、稳定且有高质量样例的任务，才评估微调或蒸馏；把训练、维护和持续评测纳入总账。
- 知识频繁变化时优先维护检索资料。
- 不默认使用单字母字段、全文翻译、Base64 或某种序列化格式。以实际 Token、准确率和返工成本做比较。



## 4. 给建议排优先级

先做可观测性和低风险浪费，再做结构性改造：

1. 修复重复读取、无效重试、失控循环和过大返回。
2. 裁剪上下文、RAG 和工具载荷，补上明确停止条件。
3. 稳定缓存前缀，设计权限安全的结果缓存。
4. 用评测调整模型、推理力度、输出和升级路由。
5. 数据证明值得后，再改多 Agent 架构、批处理、微调或蒸馏。

每项建议记录：证据、成本机制、影响对象（Token/费用/时延）、预计方向或区间、置信度、实施工作量、质量与安全风险、依赖、验证和回滚条件。多个建议影响同一部分用量时避免叠加相加。

## 5. 实验与验收

- 使用相同任务集、验收器、价格口径和观察窗口比较前后结果。
- 同时观察单位成功成本、成功率、质量/安全门槛和 P95 时延。
- 分开报告冷缓存与热缓存；覆盖常见任务、长尾和关键风险场景。
- 预先写明成功、停止和回滚条件。成本下降但质量门槛未通过，不算优化成功。
- 样本不足时报告不确定性，不把一次性结果外推成稳定收益。



## 6. 常见误判

- 输入更短，所以一定更便宜。
- 缓存命中，所以统计输入 Token 必然减少。
- 流式更快看到首字，所以总成本下降。
- 多 Agent 并行，所以任务更省钱。
- 小模型单价低，所以级联必然更便宜。
- JSON、缩写或编码必然更省 Token。
- 预算耗尽停止，所以任务已经完成。

这些判断都需要端到端测量和质量验收。
